# ALEX-MIND Storage Trash and Capacity Management

## Goal
Provide a recoverable Trash area for the ALEX-MIND vault/storage layer and prevent storage exhaustion without silently losing user data.

## Status
- **Specification:** YELLOW — recorded for implementation.
- **Runtime/UI:** RED — not implemented or verified.
- **Production cleanup:** RED — no deletion or purge has been performed by this specification.

## Required behavior
1. **Soft delete first.** A user delete moves an object to Trash by changing its lifecycle/registry state and recording deletion time, original vault/path, storage provider/object key, size, checksum/version when available, and the requesting identity. Do not immediately delete the underlying blob.
2. **Trash view.** Show item name, source/vault, size, deleted date, retention deadline, and restore/permanent-delete actions. Enforce authorization and ownership on every action.
3. **Restore.** Restore metadata and object state to the original location. Verify the blob is still retrievable and integrity checks pass before reporting success. Handle name conflicts without overwriting.
4. **Permanent purge.** Purge only items whose retention period has expired, or when a user explicitly confirms permanent deletion. Record an audit event. Remove the provider object only after the database state and provider key have been validated; handle retries idempotently.
5. **Capacity monitor.** Track known object sizes and provider quota/usage when the provider exposes it. Display used/available capacity and warn at configurable thresholds (initial proposal: 80% warning, 90% critical). Label estimates as estimates when provider usage is unavailable.
6. **Safe cleanup policy.** When capacity is low, automatically purge only expired Trash items and explicitly designated regenerable cache/temp data under a documented policy. Never automatically purge active vault files, originals, user notes, project records, credentials, or unexpired Trash.
7. **If still full.** Stop or reject new uploads safely, preserve existing data, surface a clear warning, and offer a reviewable cleanup list. Do not delete important content just to force an upload.
8. **Provider independence.** Keep Trash lifecycle and audit metadata in ALEX-MIND's index; implement provider-specific delete/restore behavior behind the storage-provider interface. Account for object versioning and provider lifecycle rules.
9. **Consistency and recovery.** Use states such as active, trash_pending, trashed, restore_pending, purge_pending, purged, and failed. Add reconciliation for database/provider mismatches, retry safety, checksums, and rollback/recovery procedures.
10. **Security.** Require authentication, ownership checks, CSRF protection where applicable, audit logging, least-privilege provider credentials, and no public exposure of object keys or signed URLs.

## Proposed retention and defaults
- Default Trash retention: 30 days, configurable.
- Warn before permanent deletion; show count and total bytes.
- No automatic permanent deletion of unexpired Trash.
- Capacity thresholds are alerts, not permission to delete user data.
- Do not claim reclaimed space until provider deletion is confirmed and usage is refreshed or marked as pending/estimated.

## Implementation plan
1. Inspect current object lifecycle contract, object registry schema, B2 adapter, and production-vs-migration schema. Read-only only.
2. Design a migration for Trash metadata/state and audit events; test against a disposable database first.
3. Implement and test lifecycle transitions and authorization, including duplicate requests and provider failures.
4. Implement provider adapter delete/restore operations and verify object existence/integrity.
5. Add UI/API for Trash, restore, permanent delete, and capacity status.
6. Add unit/integration tests for restore, expired retention, full storage, provider outage, stale registry, unauthorized access, and idempotent retries.
7. Deploy only after review, backup/recovery plan, CI success, and explicit production migration checks.

## Acceptance criteria
- A soft-deleted object is recoverable during retention.
- Restore returns the verified object to its original vault/path without overwriting an existing object.
- Permanent purge cannot target active objects and is auditable/idempotent.
- Capacity alerts use measured or clearly labelled estimated values.
- Low-space cleanup never removes protected user content or unexpired Trash.
- Tests prove behavior under provider/API failure and database/provider inconsistency.
- Production storage reclaimed is confirmed rather than inferred from metadata.
