# Section 15.2 — Object Lifecycle

Status: GREEN

## Purpose
Define the logical lifecycle of an ALEX MIND object from intake through retention or failure.

## Lifecycle
An object moves through these logical states:

1. incoming — object has been accepted for processing but is not yet confirmed in storage.
2. stored — object bytes are confirmed in the configured storage backend.
3. indexed — object metadata and storage reference are recorded in the central index.
4. linked — object is associated with one or more project or knowledge records.
5. archived — object is retained as long-term material and is no longer part of active working flow.
6. failed — a required lifecycle operation did not complete successfully.

## Transition rules
- incoming → stored: only after the storage backend confirms a successful write.
- stored → indexed: only after the object reference and required metadata are persisted in the central index.
- indexed → linked: when a valid project, knowledge item, or other approved relationship is created.
- indexed → archived: allowed when the object is retained without an active project link.
- linked → archived: allowed when active use ends and retention policy requires preservation.
- any active state → failed: only when the required operation fails and the failure is recorded.
- failed → incoming: allowed only when a controlled retry starts a new processing attempt.

## Failure behavior
Failures must fail closed for state advancement.

An object must not be marked `stored` when the backend write is uncertain.
An object must not be marked `indexed` when the metadata write is uncertain.
An object must not be marked `linked` when the relationship write is uncertain.

Retries must be idempotent where possible and must not silently create duplicate logical objects.

## Provider independence
The lifecycle is ALEX MIND state, not a storage-provider lifecycle.

A provider may have its own retention, versioning, or lifecycle mechanisms. Those mechanisms must not be treated as proof that an ALEX MIND object reached a logical lifecycle state.

## Deletion and retention
Deletion is not a normal lifecycle state in Section 15.2.

Physical deletion requires an explicit retention/deletion policy and must not be inferred from a project unlink or archive action.

Archived objects remain discoverable through the central index unless a later policy explicitly removes them.

## Integrity requirements
- Each transition must be attributable to a controlled operation.
- State changes must not expose credentials or signed access material.
- Metadata and object bytes must remain separable.
- A failed operation must not be represented as successful state.
- Lifecycle state must remain consistent with the object contract in Section 15.1.

## Current implementation boundary
Section 15.2 defines the lifecycle contract only.
It does not yet add lifecycle automation, new D1 tables, new Worker endpoints, or storage-provider lifecycle rules.

Those implementation concerns are deferred until the relevant Section 15 runtime work is explicitly required.

## Acceptance criteria
Section 15.2 is complete when:
- all lifecycle states are defined;
- valid transitions are explicit;
- failure and retry behavior is fail-closed;
- deletion is separated from archive;
- provider-specific lifecycle behavior cannot redefine ALEX MIND state;
- no runtime resource is changed solely by this contract document.
