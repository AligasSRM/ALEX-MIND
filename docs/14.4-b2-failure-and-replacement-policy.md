# Section 14.4 — B2 Failure and Replacement Policy

Status: GREEN

## Failure policy
A B2 failure is isolated to the affected object operation. A provider error must not silently corrupt the D1 index or unrelated source state.

## Partial failure handling
- B2 write failure: operation fails.
- B2 read failure after write: operation fails and object is not marked verified.
- Checksum mismatch: operation fails and object is not marked verified.
- D1 indexing failure after verified storage: operation fails visibly and remains auditable; storage bytes are not silently deleted by the runtime.
- KV failure: runtime reports failure rather than pretending the complete operation succeeded.

## Replacement
B2 is an implementation of the storage-provider contract. Replacing B2 must not require changing object identity rules or the provider-independent object contract.

## Security
Credentials, signed URLs, and raw provider secrets are never persisted as object metadata.

## Acceptance
GREEN when provider failure is fail-closed, partial failures remain observable, and provider replacement does not change ALEX MIND object identity.
