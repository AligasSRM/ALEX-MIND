# Section 17.4 — Ingestion Queue & Processing State

Status: ACTIVE

## Purpose
Define the controlled processing states for material after it enters ALEX MIND ingestion and before it becomes trusted, routed, or project-linked information.

## Processing states
- received: ingestion event has been accepted into the intake boundary.
- validating: validation and normalization are in progress.
- ready: validation succeeded and the item can proceed to classification.
- processing: classification, routing, indexing, or controlled downstream work is in progress.
- completed: required ingestion processing completed successfully.
- quarantined: processing stopped because validation, policy, integrity, or authorization failed.
- failed: an unexpected processing error occurred and requires controlled recovery.
- cancelled: processing was intentionally stopped by an authorized control action.

## State transition principles
1. received -> validating when processing begins.
2. validating -> ready only after required validation succeeds.
3. ready -> processing when controlled downstream processing starts.
4. processing -> completed only after all required operations succeed.
5. validating -> quarantined when validation or policy checks fail.
6. processing -> quarantined when an integrity or authorization rule requires isolation.
7. validating or processing -> failed when an unexpected operational failure occurs.
8. received, validating, ready, or processing -> cancelled only through explicit authorized cancellation.
9. failed -> validating only through a controlled retry.
10. quarantined -> validating only through an explicit release/retry policy.
11. completed is terminal for the current ingestion attempt.

## Queue behavior
Queue ordering must be deterministic enough to support traceability.

A queue item must retain:
- ingestion identity;
- source identity;
- external identifier when available;
- current state;
- attempt count;
- created timestamp;
- last transition timestamp;
- failure or quarantine reason when applicable.

## Idempotency and retries
A retry must reuse the logical ingestion identity where appropriate.

Retries must increment or otherwise record the attempt state and must not create duplicate logical source items.

A completed item must not be reprocessed as a new item without an explicit re-ingestion operation.

## Failure handling
Unexpected failures enter failed and must preserve diagnostic metadata.

Quarantined items remain isolated from trusted project processing.

Secrets, access tokens, signed URLs, and private credentials must never be stored in queue state or failure reasons.

## Ordering and priority
Priority may be introduced by policy, but priority must not bypass validation or authorization requirements.

An older low-priority item must not be processed in a way that violates source or project isolation.

## Current implementation boundary
Section 17.4 defines queue and processing-state semantics only.

It does not create a queue service, add D1 tables, add Worker endpoints, enable background workers, or alter existing runtime ingestion behavior.

## Acceptance criteria
Section 17.4 is complete when:
- processing states are explicit;
- valid transitions are defined;
- retry behavior is idempotent;
- failures and quarantines are isolated;
- queue metadata is traceable;
- priority cannot bypass security or validation;
- no runtime resource is changed solely by this contract document.
