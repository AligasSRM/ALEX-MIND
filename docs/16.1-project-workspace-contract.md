# Section 16.1 — Project Workspace Contract

Status: ACTIVE

## Purpose
Define the project workspace as the controlled environment where active project work is performed, while the ALEX MIND Central Vault remains the external memory, source, archive, and storage coordination layer.

## Separation of responsibilities
- Central Vault stores and indexes retained information, source material, object metadata, and project-linked knowledge.
- Project Workspace is the active working environment for one project.
- A workspace may consume approved material from the Central Vault but does not replace it.
- Work performed in one project workspace must not silently become another project's working state.

## Workspace identity
Each project workspace should have:
- a stable workspace identifier;
- a project identifier;
- an explicit status;
- an owner/control boundary;
- references to approved vault objects and knowledge;
- timestamps for creation and updates.

## Project isolation
Each workspace belongs to exactly one logical project.

Sharing a storage provider, backend, or Central Vault does not merge workspaces.

Cross-project reuse must occur through an explicit reference or controlled transfer. It must not copy or expose unrelated project data by default.

## Vault relationship
A workspace may read or receive approved objects from the Central Vault.

The workspace must not assume that every vault object belongs to it.

Changes made during active work should be traceable to the workspace and, when appropriate, written back to the Central Vault through controlled synchronization.

## Status boundary
A workspace may be:
- active;
- paused;
- locked;
- archived.

A locked or archived workspace must not accept normal active work without an explicit controlled transition.

## Security boundary
Workspace access must follow the project's authorization boundary.

Secrets, credentials, private keys, wallet seeds, and other sensitive access material must remain outside ordinary workspace documentation and Central Vault indexes unless a dedicated secret-management mechanism explicitly supports them.

## Current implementation boundary
Section 16.1 defines the workspace contract only.

It does not create runtime workspaces, modify existing projects, move files, change D1 schema, change Worker routes, or alter the locked Sections 1–15.

## Acceptance criteria
Section 16.1 is complete when:
- the workspace role is explicit;
- Central Vault and active work are clearly separated;
- project isolation is explicit;
- workspace identity and status are defined;
- vault-to-workspace references are controlled;
- no runtime resource is changed solely by this contract document.
