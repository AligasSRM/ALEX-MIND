# Section 18.4 — Knowledge Relationships & Retrieval

Status: ACTIVE

## Purpose
Define how knowledge records relate to each other and how ALEX MIND retrieves relevant knowledge without breaking source, project, or security boundaries.

## Relationship model
Knowledge may relate to:
- source material;
- other knowledge;
- projects;
- workspaces;
- decisions;
- objects;
- archived records.

Relationships should identify their direction and semantic purpose where needed.

## Source traceability
Every derived knowledge record must retain a path back to the source records that support it.

Retrieval must not detach knowledge from its provenance.

## Relationship integrity
Broken, ambiguous, or conflicting relationships must be detectable.

A missing relationship must not be silently replaced with an invented reference.

## Retrieval scope
Retrieval should evaluate, in order:
1. security and authorization boundary;
2. project scope;
3. knowledge lifecycle state;
4. temporal validity;
5. source relevance;
6. evidence and confidence;
7. semantic relevance.

Security and scope constraints take precedence over relevance.

## Active versus historical retrieval
Normal retrieval should prefer active, validated knowledge.

Superseded and archived records may be returned when historical context, auditability, or explicit user intent requires them.

Rejected knowledge must not appear in normal active retrieval.

## Conflict-aware retrieval
When relevant knowledge contains unresolved conflicts, retrieval should preserve the conflict state and distinguish the competing records rather than presenting one as established truth without evidence.

## Project isolation
Project-specific knowledge must remain isolated from unrelated project retrieval unless an explicit cross-project relationship or approved global scope exists.

## Ranking
Relevance ranking is advisory.

A highly relevant record must not outrank a required security or scope restriction.

Confidence must not be fabricated to improve ranking.

## Deduplication
Equivalent records may be linked or consolidated according to policy, but consolidation must preserve provenance and historical traceability.

## Failure behavior
If required scope, authorization, or provenance information is unavailable, retrieval must fail closed or return only information whose safety and scope can be established.

## Security
Retrieval must never expose:
- passwords;
- API keys;
- private keys;
- wallet seeds;
- authentication tokens;
- secrets embedded in metadata.

## Implementation boundary
This document defines relationship and retrieval semantics only.

It does not add search infrastructure, vector databases, runtime endpoints, automatic ranking, or database schema changes, and it does not modify Sections 1–17.

## Acceptance criteria
Section 18.4 is complete when:
- relationship types and provenance are defined;
- retrieval precedence is explicit;
- active and historical retrieval are distinguished;
- conflicts remain visible;
- project isolation is preserved;
- ranking cannot bypass security or scope;
- missing provenance fails safely;
- secrets are excluded from retrieval.
