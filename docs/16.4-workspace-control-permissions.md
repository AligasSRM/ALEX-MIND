# Section 16.4 — Workspace Control & Permissions

Status: ACTIVE

## Purpose
Define the authorization and control boundary for ALEX MIND project workspaces.

## Control principles
1. Every workspace has one explicit project identity.
2. Workspace actions must be authorized against that project boundary.
3. Access to one workspace does not imply access to another workspace.
4. Vault access is granted through approved references and policy, not through storage-provider access alone.
5. Locked and archived workspaces reject normal write operations.
6. Authorization failures fail closed.

## Permission classes
A workspace control layer should distinguish at least:
- read: inspect approved workspace and vault-linked material;
- write: create or modify active project work;
- link: create approved relationships to vault objects or knowledge;
- archive: move the workspace into retained non-active state;
- lock: freeze normal changes;
- reopen: explicitly restore a locked or archived workspace to active state.

## Project boundary
Permissions are evaluated within the workspace's project context.

A user or control process authorized for Project A must not gain Project B access merely because both projects use the same backend, vault, or Worker.

Cross-project access requires an explicit approved relationship or controlled transfer.

## Vault boundary
Workspace permission does not grant unrestricted Central Vault access.

Only objects and knowledge approved for the workspace may be consumed or linked.

Sensitive material must remain excluded unless a dedicated policy explicitly authorizes its use.

## State-aware permissions
- planned: no normal project writes.
- active: normal authorized project operations allowed.
- paused: normal active writes should be blocked unless explicitly resumed.
- locked: writes and structural changes blocked.
- archived: normal project operations blocked; controlled read/reference may remain available.
- reopen: requires an explicit controlled authorization.

## Audit requirements
Control decisions should be attributable to:
- workspace;
- project;
- operation;
- actor or control process;
- decision;
- timestamp;
- relevant object or record when applicable.

Audit records must not contain secrets or private access material.

## Fail-closed behavior
Unknown workspace, unknown project, missing authorization, ambiguous policy, or invalid state transition must result in denial rather than best-effort access.

## Current implementation boundary
Section 16.4 defines the permission contract only.

It does not implement authentication, add authorization endpoints, modify Cloudflare bindings, create new D1 tables, or change existing project permissions.

## Acceptance criteria
Section 16.4 is complete when:
- permission classes are explicit;
- project and vault boundaries are separated;
- workspace state affects allowed operations;
- authorization failures fail closed;
- audit requirements are defined without storing secrets;
- no runtime resource is changed solely by this contract document.
