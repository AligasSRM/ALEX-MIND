# Section 16.3 — Workspace ↔ Vault Integration Contract

Status: ACTIVE

## Purpose
Define the controlled relationship between an active project workspace and the ALEX MIND Central Vault.

## Core principle
The Central Vault is the retained memory and coordination layer.
The Project Workspace is the active execution layer.

The workspace may consume approved vault material, and approved project results may be returned to the vault, but neither layer silently replaces the other.

## Read path
A workspace may request:
- approved objects;
- project-linked knowledge;
- source records;
- relevant metadata;
- prior project checkpoints.

Reads must respect the project's authorization and project relationship.

A workspace must not receive unrelated project material merely because it exists in the same vault or storage provider.

## Write-back path
Project work may produce:
- new objects;
- updated project documents;
- decisions;
- checkpoints;
- knowledge;
- references to external source material.

Write-back to the Central Vault must preserve:
- project identity;
- source attribution when applicable;
- object identity;
- lifecycle state;
- timestamps;
- applicable routing metadata.

## Sync direction
Vault-to-workspace and workspace-to-vault synchronization are separate operations.

A successful read does not imply a write-back.
A successful write-back does not imply that every workspace file is now stored in the vault.

## Conflict handling
If workspace content and retained vault content disagree, the system must not silently overwrite either side.

Conflict resolution must identify:
- the workspace;
- the affected object or record;
- the conflicting versions;
- the operation that detected the conflict.

The resolution must be explicit and traceable.

## Object handling
When a workspace references a vault object, it should use the object's stable identity rather than duplicating the object's bytes unnecessarily.

When new bytes are produced, the object lifecycle from Section 15 must apply before the result is treated as retained project material.

## Project isolation
Integration must preserve project boundaries.

A workspace may reference shared approved knowledge where policy allows, but project-private material must not become visible to another workspace through automatic synchronization.

## Security boundary
Credentials, access tokens, signed URLs, private keys, wallet seeds, and similar secrets must not be copied into ordinary workspace-vault synchronization records.

## Current implementation boundary
Section 16.3 defines the integration contract only.

It does not add synchronization endpoints, create new D1 tables, move B2 objects, enable automatic sync, or change existing Sections 1–15.

## Acceptance criteria
Section 16.3 is complete when:
- read and write-back paths are explicit;
- sync direction is separated;
- conflicts fail safely;
- object identity is preserved;
- project isolation is enforced;
- secrets remain outside ordinary synchronization records;
- no runtime resource is changed solely by this contract document.
