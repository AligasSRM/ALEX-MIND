# Section 16.2 — Project Workspace Lifecycle

Status: ACTIVE

## Purpose
Define the controlled lifecycle of an ALEX MIND project workspace from creation through active work, pause, lock, archive, and controlled recovery.

## Lifecycle states
- planned: workspace is defined but not yet active.
- active: workspace is authorized for normal project work.
- paused: active work is temporarily stopped while the workspace remains retained.
- locked: workspace is frozen against normal changes pending explicit controlled reopening.
- archived: workspace is retained for historical/reference purposes and is no longer an active work environment.

## Valid transitions
1. planned -> active: only after the workspace has its required project identity and control boundary.
2. active -> paused: when active work is intentionally suspended.
3. paused -> active: when controlled project work resumes.
4. active -> locked: when a stable checkpoint must be protected.
5. paused -> locked: when the paused state must be frozen.
6. locked -> active: only through an explicit controlled reopen.
7. active -> archived: only when active work has ended and retention is required.
8. paused -> archived: allowed when the project is no longer actively worked.
9. locked -> archived: allowed when the locked checkpoint is retained as historical state.

## Fail-closed behavior
An invalid or ambiguous transition must not silently change workspace state.

A workspace must not become active merely because files are present, and an archived or locked workspace must not accept ordinary work without an explicit transition.

## Project isolation
Workspace lifecycle changes apply only to the workspace's own project.

Locking, pausing, or archiving one project must not change the lifecycle of another project, even when both use the same Central Vault or storage provider.

## Relationship with Central Vault
Pausing, locking, or archiving a workspace does not delete its Central Vault objects or index records.

When a workspace is archived, retained objects remain discoverable according to the object lifecycle and retention policies in Sections 15.2–15.4.

## Recovery
A paused workspace may resume through the normal controlled transition.

A locked or archived workspace requires an explicit authorization step before returning to active work. Recovery must preserve project identity and existing references.

## Idempotency
Repeated lifecycle requests for the same target state must not create duplicate workspaces or alter unrelated projects.

## Current implementation boundary
Section 16.2 defines lifecycle semantics only.

It does not create runtime workspace records, add D1 tables, add Worker endpoints, move objects, or reopen locked Sections 1–15.

## Acceptance criteria
Section 16.2 is complete when:
- workspace states are explicit;
- valid transitions are defined;
- invalid transitions fail closed;
- project isolation is preserved;
- Central Vault retention is preserved;
- recovery is controlled and idempotent;
- no runtime resource is changed solely by this contract document.
