# Section 18.2 — Knowledge Lifecycle

Status: ACTIVE

## Purpose
Define the controlled lifecycle of knowledge records inside ALEX MIND.

## Lifecycle states
A knowledge record may move through these states:

1. candidate
2. validated
3. active
4. superseded
5. archived
6. rejected

## Candidate
Information becomes a candidate only after the applicable source-ingestion and classification boundaries have been satisfied.

Candidate knowledge is not treated as verified active knowledge.

## Validated
A candidate becomes validated when the required evidence, provenance, and quality checks have passed.

Validation requirements depend on knowledge type and source context.

## Active
Active knowledge is available for normal retrieval and project use within its defined scope.

Active does not mean universally true; scope, provenance, and confidence remain part of the record.

## Superseded
Knowledge becomes superseded when a newer authoritative record replaces it for the same scope.

The prior record remains traceable and is not silently deleted.

## Archived
Archived knowledge is retained for historical or recovery purposes and is excluded from normal active retrieval unless explicitly requested or required by policy.

## Rejected
Knowledge is rejected when it fails required validation, provenance, security, or classification rules.

Rejected material must not be presented as active knowledge.

## Transitions
Allowed transitions must be explicit:

candidate → validated
candidate → rejected
validated → active
validated → rejected
active → superseded
active → archived
superseded → archived

A transition must not silently cross project or security boundaries.

## Provenance
Lifecycle changes must preserve:
- source references;
- project scope;
- timestamps;
- reason for significant state changes;
- relationship to superseding records where applicable.

## Idempotency
Repeated processing of the same source-derived knowledge must not create uncontrolled duplicate active records.

Stable identity and source references should be used to recognize repeated input.

## Failure behavior
If required validation or provenance information is unavailable, processing must fail closed rather than promote uncertain information to active knowledge.

## Project isolation
A lifecycle transition must preserve the knowledge record's project scope.

A project-specific record must not become global through a lifecycle transition alone.

## Security boundary
Knowledge lifecycle operations must not expose or persist secrets such as passwords, API keys, private keys, wallet seeds, or authentication tokens.

## Implementation boundary
This document defines lifecycle behavior only.

It does not add runtime endpoints, automatic extraction, background workers, or new database schema, and it does not modify or reopen Sections 1–17.

## Acceptance criteria
Section 18.2 is complete when:
- lifecycle states are explicit;
- transitions are defined;
- provenance is preserved;
- superseded history remains traceable;
- rejected information cannot become active silently;
- duplicate processing is controlled conceptually;
- failures remain fail-closed;
- project and security boundaries are preserved.
