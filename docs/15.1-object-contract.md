# Section 15.1 — Object Contract

Status: GREEN

## Purpose
Define the provider-independent contract for a stored object in ALEX MIND.
The object contract describes metadata and identity. It does not store file bytes in D1 and does not depend on Backblaze B2 as the permanent provider.

## Separation of responsibilities
- Storage provider: stores and retrieves object bytes.
- Cloudflare Worker: controls access, routing, validation, and lifecycle operations.
- D1: stores searchable object metadata and relationships.
- KV: stores lightweight runtime/control state only.
- Project workspaces: consume objects through indexed references.
- Vaults: define the logical storage destination and policy.

## Required object identity
Every managed object must have:
- object_id: stable ALEX MIND identifier.
- source_id: originating source record.
- vault_id: logical vault destination.
- storage_provider: provider identifier, such as backblaze-b2.
- storage_bucket: provider bucket/container name.
- storage_key: provider object key/path.
- status: lifecycle state.

object_id is the ALEX MIND identity. The provider key is an implementation detail and must not become the global identity.

## Recommended metadata
An object record may include:
- name
- kind
- mime_type
- size_bytes
- checksum
- checksum_algorithm
- created_at
- updated_at
- stored_at
- archived_at
- external_id
- metadata_json

Metadata must remain bounded and structured. Large file contents belong in the storage backend, not D1.

## Lifecycle states
The contract permits:
- incoming
- stored
- indexed
- linked
- archived
- failed

State transitions are defined separately by Section 15.2.

## Integrity rules
1. object_id must be unique.
2. A stored object must have a valid provider, bucket, and storage key.
3. size_bytes must describe the stored object when known.
4. A checksum should be recorded when the provider or ingestion path can calculate one.
5. Secrets, access keys, signed URLs, and credentials must never be stored in object metadata.
6. D1 contains references and metadata, not the object payload.
7. Provider replacement must not require changing the ALEX MIND object identity.

## Vault and project separation
An object may be linked to one or more projects through relationship records, but its physical storage location remains controlled by the vault/storage policy.
The object contract therefore does not embed project-specific storage rules.

## Current backend
The current implementation uses the private Backblaze B2 bucket alex-central-vault.
This is an implementation of the storage contract, not a change to the contract itself.

## Non-goals
This file does not:
- add a new D1 table;
- change the existing Worker;
- move existing objects;
- change B2 configuration;
- define routing rules;
- define lifecycle automation;
- expose credentials.

Those concerns belong to later Section 15 files.

## Acceptance criteria
Section 15.1 is complete when:
- the object identity is provider-independent;
- storage metadata is clearly separated from object bytes;
- vault/project relationships are explicit;
- integrity and secret-handling rules are defined;
- no runtime resource is changed solely by this contract document.
