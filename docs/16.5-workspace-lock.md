# Section 16.5 — Workspace Lock

Status: GREEN / CLOSED

## Purpose
Lock the Project Workspace contract after defining workspace identity, lifecycle, vault integration, and permissions.

## Locked principles
1. A Project Workspace is the active execution environment for one project.
2. The Central Vault remains the retained memory, indexing, and coordination layer.
3. Workspace lifecycle follows Section 16.2 and invalid transitions fail closed.
4. Workspace-to-vault integration follows Section 16.3 with explicit read and write-back paths.
5. Permissions follow Section 16.4 and remain scoped to the workspace's project.
6. Shared storage providers do not merge project workspaces.
7. Locked and archived workspaces reject normal active writes.
8. Cross-project access requires an explicit approved relationship or controlled transfer.
9. Secrets and private access material remain outside ordinary workspace records.
10. Runtime implementation must consume these contracts without silently rewriting them.

## Section 16 acceptance checks
- 16.1 Project Workspace Contract exists.
- 16.2 Project Workspace Lifecycle exists.
- 16.3 Workspace ↔ Vault Integration Contract exists.
- 16.4 Workspace Control & Permissions exists.
- Workspace/project isolation is preserved.
- Central Vault and active project work remain separate.
- No runtime endpoint, D1 schema, storage migration, or permission system was introduced by Section 16 documentation.

## Lock boundary
Section 16 is a contract/documentation layer only.

Future runtime implementation may use these contracts, but the Section 16 documents must not be reopened or rewritten unless a concrete technical inconsistency or failed runtime test proves that a correction is required.

GREEN / CLOSED / LOCKED
