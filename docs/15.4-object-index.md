# Section 15.4 — Object Index

Status: GREEN

## Purpose
Define how ALEX MIND records the identity and location of stored objects in the central index without storing the object bytes in D1.

## Index role
The central index is the authoritative discovery layer for object metadata and routing relationships.

For each indexed object, the index should be able to identify:
- object_id
- source_id
- vault_id
- project relationship when applicable
- storage_provider
- storage_bucket
- storage_key
- lifecycle status
- object name and kind when available
- MIME type and size when available
- checksum and checksum algorithm when available
- created, updated, stored, and archived timestamps when applicable
- external_id when supplied by the source

## Separation of metadata and bytes
D1 stores object metadata, references, relationships, and lifecycle state.

The actual file/object bytes remain in the configured storage backend.

The index must never treat metadata alone as proof that bytes exist. A stored state requires successful storage confirmation as defined by Section 15.2.

## Integrity
Where a checksum is available, it should be retained with its algorithm and used for integrity verification.

Provider-specific object identifiers and keys must be preserved exactly enough to locate the object without exposing credentials or signed access material.

## Relationships
Project and knowledge relationships are index-level relationships. They must not duplicate the underlying object bytes.

An object may be linked to approved project or knowledge records while retaining a single primary vault assignment.

## Missing or stale objects
If an indexed object cannot be confirmed in the storage backend, it must not be presented as verified storage.

The index should retain the metadata needed for controlled recovery or reconciliation rather than silently deleting the record.

## Provider replacement
Changing storage providers must not require changing the logical object identity.

A migration may update provider-specific storage metadata while preserving object_id and existing project/knowledge relationships.

## Current implementation boundary
Section 15.4 defines the indexing contract only. It does not add a new D1 schema, create runtime endpoints, migrate existing objects, or modify the Section 14 storage integration.

## Acceptance criteria
Section 15.4 is complete when:
- the central index role is explicit;
- object metadata and bytes are separated;
- required storage references are defined;
- lifecycle state is consistent with Section 15.2;
- project relationships remain index-level;
- provider replacement preserves logical identity;
- missing objects are handled without silent deletion;
- no runtime resource is changed solely by this contract document.
