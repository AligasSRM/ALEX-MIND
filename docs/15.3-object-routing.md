# Section 15.3 — Object Routing

Status: ACTIVE

## Purpose
Define how ALEX MIND routes objects between the logical Phone Vault, Work Vault, and Archive Vault without mixing their purposes.

## Vault roles
- Phone Vault: phone-originated personal files and other material explicitly approved for phone synchronization.
- Work Vault: working material used by ALEX MIND and its connected projects, including project documents and controlled source data.
- Archive Vault: long-term retained material that should remain available without belonging to the active working flow.

## Routing principles
1. Routing is policy-driven, not based on storage-provider identity.
2. An object may have one primary vault at a time.
3. Storage providers remain implementation backends and do not define vault ownership.
4. A project relationship does not automatically make an object phone-synchronized.
5. Phone synchronization is an explicit policy decision and must not be inferred from vault routing.
6. Work data and personal phone data must not be silently mixed.
7. Archive routing must preserve discoverability through the central index.

## Default routing
- Source material intended for active ALEX MIND/project work routes to Work Vault.
- Material explicitly approved for phone synchronization routes to Phone Vault.
- Material whose active use has ended but whose retention is required routes to Archive Vault.
- Unclassified material remains in the controlled intake/inbox flow until a routing decision is made.

## Project separation
Routing must preserve project boundaries. An object linked to XKiss, Alex Bitcoin, AC Assist Center, Style & Looks, or another project must retain its project relationship while remaining physically and logically separated from unrelated project data.

No routing rule may merge project workspaces merely because they share the same storage backend.

## Routing metadata
A routed object should be represented in the central index with, at minimum:
- object_id
- vault_id
- source_id
- project relationship when applicable
- storage provider
- storage bucket
- storage key
- lifecycle status

The object bytes remain in the storage backend; the central index stores the routing and discovery metadata.

## Conflict handling
If multiple policies apply, routing must fail closed rather than silently selecting an unsafe destination.

A controlled policy-resolution step must determine the primary vault before physical movement or synchronization occurs.

## Current implementation boundary
Section 15.3 defines routing semantics only. It does not move existing B2 objects, change the Section 14 backend, add Worker endpoints, alter D1 schema, or enable phone synchronization.

## Acceptance criteria
Section 15.3 is complete when:
- Phone, Work, and Archive Vault roles are explicit;
- default routing rules are explicit;
- project separation is preserved;
- phone synchronization is not inferred;
- routing conflicts fail closed;
- provider identity does not determine vault ownership;
- no runtime resource is changed solely by this contract document.
