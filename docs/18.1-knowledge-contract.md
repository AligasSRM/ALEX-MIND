# Section 18.1 — Knowledge Contract

Status: ACTIVE

## Purpose
Define the controlled knowledge layer of ALEX MIND as reusable, traceable information derived from validated sources, project work, and approved records.

## Knowledge is not raw intake
Raw source material remains in the ingestion boundary until validated and classified.

Knowledge must not be created merely because an item entered the Central Vault.

A knowledge record represents information that has passed the applicable validation and classification rules.

## Knowledge identity
Each knowledge record should have:
- a stable knowledge identifier;
- title or concise description;
- knowledge type;
- source references;
- project references when applicable;
- confidence or validation status when applicable;
- created and updated timestamps;
- lifecycle status.

## Source traceability
Knowledge must retain traceability to its source material.

A knowledge record must not erase or replace the original source relationship.

When knowledge is derived from multiple sources, the contributing source references should remain distinguishable.

## Project context
Knowledge may be:
- global/reusable;
- project-specific;
- source-specific;
- archived.

Project-specific knowledge must retain its project boundary and must not become globally reusable merely because it is stored in the Central Vault.

## Knowledge quality
Knowledge should distinguish:
- verified information;
- derived interpretation;
- unresolved information;
- obsolete or superseded information.

Uncertain information must not be represented as verified fact.

## Relationships
Knowledge may reference:
- source objects;
- other knowledge records;
- project workspaces;
- decisions;
- archived material.

Relationships are metadata links and must not duplicate the underlying object bytes unnecessarily.

## Updates
A knowledge update must preserve history or sufficient provenance to determine what changed and why.

Superseding a knowledge record must not silently destroy the prior record when historical traceability is required.

## Security
Secrets, passwords, wallet seeds, private keys, access tokens, and signed URLs must never be stored as ordinary knowledge content.

## Current implementation boundary
Section 18.1 defines the knowledge contract only.

It does not create a knowledge database, add Worker endpoints, enable automatic knowledge extraction, modify existing D1 schema, or reopen Sections 1–17.

## Acceptance criteria
Section 18.1 is complete when:
- knowledge identity is defined;
- raw intake is separated from knowledge;
- source traceability is preserved;
- project context is explicit;
- quality states are distinguishable;
- relationships are metadata-based;
- sensitive access material is excluded;
- no runtime resource is changed solely by this contract document.
