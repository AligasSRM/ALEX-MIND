# Section 17.2 — Ingestion Validation & Normalization

Status: ACTIVE

## Purpose
Define how newly ingested source material is validated and normalized before it can be indexed, routed, linked, or used by a project workspace.

## Validation stages
1. Source validation: confirm that the source is registered, active, and authorized for ingestion.
2. Envelope validation: confirm required ingestion metadata is present.
3. Identity validation: preserve the source identity and external identifier when available.
4. Content validation: verify that the incoming item has an acceptable kind and usable content or object reference.
5. Policy validation: confirm that vault synchronization and applicable source policies allow ingestion.
6. Deduplication check: determine whether the same source item has already been ingested.

A failed stage must stop normal progression.

## Normalization
Normalization may standardize metadata needed by ALEX MIND, including:
- source identifiers;
- content kind;
- timestamps;
- MIME type when available;
- external identifiers;
- normalized titles;
- structured metadata.

Normalization must preserve the original source identity and must not alter the authoritative source content in a way that changes its meaning.

## Raw preservation
The original incoming representation must remain distinguishable from normalized metadata.

Normalization is metadata processing, not permission to rewrite or destroy source material.

## Deduplication
When a stable external identifier exists, it should be the primary deduplication reference within the source boundary.

Where no stable identifier exists, deduplication may use controlled fingerprints or other deterministic metadata.

Deduplication must not merge unrelated items merely because their content appears similar.

## Quarantine and failure
Items that fail validation, policy checks, or integrity checks must be rejected or quarantined according to the applicable policy.

They must not advance to trusted project state.

Failure records must not contain credentials, access tokens, signed URLs, or other secrets.

## Project separation
Validation and normalization must remain independent of project assignment.

An item can be valid and normalized while still remaining unclassified or unlinked to any project.

## Idempotency
Repeating validation or normalization on the same logical source item must not create duplicate logical records or change its source identity.

## Current implementation boundary
Section 17.2 defines validation and normalization semantics only.

It does not implement source connectors, add runtime endpoints, modify D1 schema, alter current source policies, or enable automatic ingestion.

## Acceptance criteria
Section 17.2 is complete when:
- validation stages are explicit;
- normalization preserves source meaning and identity;
- raw material remains distinguishable;
- deduplication is source-aware;
- failures fail closed;
- project assignment remains separate;
- repeated processing is idempotent;
- no runtime resource is changed solely by this contract document.
