# Section 14.3 — B2 Write, Read and Integrity Verification

Status: GREEN

## Purpose
Define the minimum evidence required before an object is considered stored.

## Required flow
1. Validate source and vault policy.
2. Calculate SHA-256 for the object bytes.
3. Write the object to B2.
4. Read the same object back from B2.
5. Calculate SHA-256 for the returned bytes.
6. Compare the checksums.
7. Only after successful verification, create the D1 object record with status stored.
8. Update lightweight KV runtime state.

## Fail-closed rule
If write, read, or checksum verification fails:
- the object must not be reported GREEN;
- D1 must not claim the object is verified/stored;
- the failure must be surfaced to the caller and logs.

## Production evidence
The Section 20.1 runtime implements this sequence. Existing production D1 object records use the B2 provider and stored lifecycle state, which is only written after the runtime verification path succeeds.

## Acceptance
GREEN when B2 write/read/verification precedes D1 storage-state completion.
